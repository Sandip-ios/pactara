- Feed media URLs are signed in deduplicated batches per storage bucket, and feed videos load only near the viewport to avoid competing downloads.
- Sign storage images through `src/lib/media-urls.ts` (resized via image transforms); videos get a `<path>.poster.jpg` preview frame uploaded at check-in. Why: raw uploads are 2–25 MB and made the feed slow.
- Wrap feed/profile query results in `stabilizeSignedUrls` so refetches reuse the same signed URL. Why: a fresh token makes the browser re-download the same media.
- Bridge native app state to React Query's focus manager; member-photo failures show initials until a fresh URL arrives. Why: suspended WebViews can retain expired photo links without emitting browser focus events.
- Build the founder Overview period summary through `period-summary.ts`, using the same UTC date bounds as the selected range and unique user-day commitments. Why: a fixed yesterday summary contradicted the date selector and cross-group copies inflate activity.
- The daily commitment is retired: keep `daily_posts.morning_ritual_*`/`morning_missed` columns only so old posts render; never write them, and keep `/api/public/hooks/morning-ritual-reminder` a no-op. Why: the hourly cron still calls that URL and historic feed cards still read the columns.
- Feed notification links use `/home?group=<id>&post=<id>` built via `src/lib/feed-deeplink.ts`; Home switches to that group and then clears the query. Why: the feed shows one group at a time, so a link without the group left people in the wrong group.
- Streak, week and rest-day math lives in `src/lib/streak-rules.ts` (pure, local dates), the nightly decision in `src/lib/auto-miss-plan.ts` and the 9 PM at-risk decision in `src/lib/streak-risk-plan.ts`; screens and jobs must use them instead of their own date loops. Why: copies drifted into UTC dates and daily-only logic.
- Home's top section (crew bar, Today card, Crew today) reads one batched `getHomeCrew` call (`src/lib/home-crew.functions.ts`); per-member today status, Mon–Sun dots and copy live in pure `src/lib/crew-today.ts` on top of streak-rules. Why: each member's day must use their own timezone and match the weekly line, without one query per member.
- "New member" (How Pactara works pill and tooltip) means account age from `profiles.created_at`, via `src/lib/new-member.ts`. Why: group join dates made long-time members look new whenever they started a group.
- The Home feed and group Activity tab both render `src/components/feed/FeedList.tsx` and load it through `useGroupFeed` (7 viewer-local days per page, `getGroupFeed({ before })`); day grouping, quiet rows, Day n and cheer wording live in pure `src/lib/feed-days.ts` / `src/lib/feed-view.ts`. Why: one feed layout with testable rules, and both screens share the same paged cache key.
- Tap-the-clock scroll-to-top goes through `useStatusBarScrollToTop` (`src/lib/status-bar-scroll.ts`): native iOS listens for Capacitor's `statusTap` window event, iOS web keeps the document parked 2px down; pages mark their scroll container with `data-scroll-root`; parking stands down while any sheet/dialog/menu locks scrolling. Why: our screens scroll inside fixed divs, which blocks the built-in iOS tap-to-top, and re-scrolling under a lock fights the overlay.
- Feed/mobile action menus open as a bottom sheet (`Drawer`), not a Radix `DropdownMenu`. Why: the modal dropdown opens on finger-down and locks page scroll, which is what preceded the iPhone crash on the own-post menu.
- The 8 PM, 9 PM and any personal daily reminder in the 8–9 PM hours share one slot per member per local day: decide with `src/lib/evening-push-plan.ts` and claim `evening_push_sends` via `claim_evening_push` before sending. Why: per-group rules let both go out the same night, and a claim row keeps repeat or overlapping runs to one push.
- Groups list, crew page and check-in celebration judge each teammate only by their own today via `memberOwnToday` (`src/lib/group-today-view.ts`, built on Home's `crewTodayStatus`). Why: viewer-date rows made teammates already on tomorrow look checked in.
- Workout plans: catalog and per-user progress live in `plans`/`plan_days`/`user_plans`/`plan_workout_logs`; next-day/week/completion math is pure in `src/lib/workout-plans.ts`, applied server-side in `plan-progress.server.ts` from `recordCheckIn`. A plan day reaches the check-in only through `src/lib/plan-checkin.ts` (armed when a logged plan workout for the plan's next day finishes). Why: plan check-ins must count exactly like any other check-in, and stale plan days must never tag unrelated check-ins.
- Logged workouts: exercise catalog in `exercises` (RepDB rows + member-owned customs), sets in `workout_set_logs`, saved templates in `workouts`, the session summary on `workout_sessions` (`logged_at`/`summary`/`check_in_ids`); prefill, progression tips and PR rules are pure in `src/lib/lift-rules.ts`, in-progress state in `src/lib/active-workout.ts`, and a finished workout reaches the post only through `recordCheckIn({ workoutSessionId })`. Why: a logged workout must count exactly like any check-in and the rules must stay testable.
- A plan day is a full page (`plans.$slug_.day.tsx`, `?week=&day=`); its blocks, dose wording and chips are pure in `src/lib/plan-day-view.ts`, and only the plan's next day carries the plan tag when started. Why: any day is browsable for free, but plan progress must only move in order.
- Full-screen pages that scroll inside their own fixed container attach `useOpenAtTop` (`src/lib/use-open-at-top.ts`) to it. Why: the router's scroll memory copies the previous page's container position onto the next page with the same selector.
- Exercise How to is one full page (`exercises.$exerciseId_.how-to.tsx`, `?swap=<liveExerciseId>` when opened from a workout); what it shows is composed in pure `src/lib/how-to-view.ts`: plan-authored fields (`plain`, `mistakes`, `easier`, `harder` on `plan_days.moves`) win, RepDB description/steps/tips and same-group beginner variation fill the rest, and missing plan copy is left out, never invented. Why: plan moves carry our own coaching copy while library-only moves rely on RepDB.
- Building a workout never starts one: picker → `WorkoutBuilder` (New/Edit workout) saves to `workouts` via `saveBuiltWorkout` (leaves `last_done_at` alone); only an explicit Start calls `useStartWorkout`. Set defaults, time estimate and My workouts order are pure in `src/lib/workout-builder.ts`. Why: members build days in advance and must find them later, not land in a running timer.
- Start a workout and the Workouts tab share one build/edit/start flow (`src/components/workout/MyWorkoutsFlow.tsx`); the Workouts tab reads one authenticated overview (`src/lib/workouts-tab.functions.ts`) whose week tiles, recent meta and lift deltas are pure in `src/lib/workouts-tab.ts`. Why: two entry points must behave identically and the numbers stay testable.
- Leaving a plan sets `user_plans.status = stopped` (never deletes); resume picks the newest stopped run and "start over" makes a fresh run. Why: history, plan chips and personal bests must survive leaving or switching.
- Cold launch: `/` decides the first screen once via `resolveLaunch` (`src/lib/launch-start.ts`, priority in pure `src/lib/launch-route.ts`) with all checks in parallel; the launch screen (`SplashScreen.tsx`, lifecycle in `src/lib/launch-screen.ts`) lifts when the router settles off `/` and no `useLaunchHold` is pending (2.5s cap); notification taps go through `src/lib/launch-links.ts`. Why: one continuous launch screen, no fixed timers, no flash of Home before the real destination.
- Workout sharing: copy/snapshot/name/wording rules are pure in `src/lib/workout-share.ts`; saved copies record `workouts.source_session_id` / `source_share_code` / `source_user_id` (one copy per source, unique index); share links live in `shared_workouts` with owner-only RLS and are read by code only through `getSharedWorkout` (service client in `shared-workouts.server.ts`, public fields only); a signed-out link keeps its code in `pending-shared-workout.ts` and Home saves it via `useClaimSharedWorkout`; `/workouts?edit=<id>` opens Edit workout. Sending to a crew chat stores the same snapshot code on `group_messages.shared_workout_code` (insert rule: the code must be the sender's), one card per crew per snapshot, via `sendWorkoutToCrew`; chat cards read public fields through `loadChatWorkoutCards`. Why: links must work signed out without exposing weights, history or crews, and copies must never duplicate.
